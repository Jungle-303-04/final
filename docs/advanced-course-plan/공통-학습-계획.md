## 공통 학습 및 프로젝트 계획

아래 내용은 네 명이 공통으로 사용하는 계획입니다. 역할은 나누지만, 각자 맡은
부분만 알고 끝내지 않도록 학습 범위와 코드 이해에 대한 책임은 함께 갖습니다.

### 1. 왜 3개월을 더 공부하려고 하는가

저희는 정글에서 자료구조와 알고리즘, C와 컴퓨터 구조, PintOS, 웹·DB,
LLM·RAG·MCP를 공부하고 팀 프로젝트까지 마쳤습니다. 짧은 시간 안에 낯선
기술을 익히고 서비스를 끝까지 만들어 본 경험은 분명히 얻었습니다.

하지만 프로젝트가 끝난 뒤 코드를 다시 보면서 부족한 점도 확인했습니다.
기능은 많았지만 모든 팀원이 전체 구조를 이해하지 못했고, AI가 작성한 코드를
충분히 검토하지 않은 채 합친 부분도 있었습니다. 담당자가 바뀌면 코드를
분석하거나 수정하기 어려웠고, 왜 그런 구조를 선택했는지 남아 있지 않은
경우도 있었습니다.

세 프로젝트 모두 한 사람이 짧은 시간 안에 전체를 이해하기 어려울 만큼
범위가 컸습니다. 예를 들어 김희준의 기존 저장소에는 Python 파일 561개,
TypeScript·TSX 파일 280개, 테스트 파일 164개가 있습니다. 실시간 데이터,
주문, AI 분석과 AWS 배포를 모두 경험했다는 장점은 있지만, 이렇게 큰
프로젝트를 짧은 기간에 만들다 보니 기술을 사용한 경험과 기술을 이해했다는
증거가 같지는 않았습니다.

이번 3개월은 새로운 기술 목록을 더 늘리기 위한 시간이 아닙니다. 정글에서
넓게 경험한 내용을 다음과 같이 바꾸기 위한 시간입니다.

| 지금까지 얻은 경험 | 이번에 보완할 점 | 3개월 뒤 남길 증거 |
|---|---|---|
| CS와 웹·AI 전반을 빠르게 학습함 | JVM과 Spring에서 원리가 어떻게 이어지는지 설명하기 어려움 | Java로 다시 만든 기능, 성능 측정과 통합 테스트 |
| 규모가 큰 팀 프로젝트를 완성함 | 담당자가 아닌 코드를 이해하고 수정한 경험이 부족함 | 코드 설명 기록과 전원의 교차 수정 PR |
| Kafka, Outbox, RAG, MCP 등을 사용함 | 왜 선택했는지, 언제 실패하는지 판단 근거가 부족함 | 아키텍처 결정 기록과 실패 상황 테스트 |
| 발표와 시연이 가능한 결과물을 만듦 | 실제 사용자가 반복해서 썼다는 근거가 없음 | 팀 내부 4주 사용 기록과 외부 사용자 재사용 결과 |
| AI로 구현 속도를 높임 | 생성된 코드에 대한 사람의 소유권이 약해짐 | 작성자 설명과 비작성자 실행·수정을 거친 코드 |

첫 달을 두는 이유도 여기에 있습니다. 바로 새 프로젝트를 시작하면 익숙하지
않은 Java와 새로운 기능을 다시 AI에 맡기게 될 가능성이 높습니다. 먼저 기존
프로젝트를 정리하고 작은 기능을 Java로 옮기면서 팀의 개발 방식을 바꾼 뒤,
남은 두 달 동안 그 방식이 실제 제품 개발에서도 유지되는지 확인하겠습니다.

### 3. 첫 달: 이전 프로젝트 정리와 다음 프로젝트 준비

첫 달에는 이전 프로젝트에 기능을 더 붙이지 않습니다. 각 프로젝트에서 핵심
흐름 하나를 골라 직접 실행하고, 어느 코드와 데이터베이스를 거치는지
정리합니다. 그 흐름을 Java와 Spring으로 다시 만들어 보면서 기존 코드를
그대로 번역할 부분과 Java에 맞게 바꿀 부분을 구분합니다.

#### 3.1 정리할 기존 프로젝트

| 대상 | 어떤 프로젝트인가 | 첫 달에 살펴볼 흐름 | Java로 옮길 범위 |
|---|---|---|---|
| 최우녕·이민정 | 쿠버네티스에서 장애 증거를 모아 원인을 찾고, 사람이 검토할 수 있는 GitOps 복구 PR을 제안한 프로젝트 | 증거 수집, 장애 판단, 복구 제안, 이벤트 재처리와 감사 기록 | `증거 입력 → 장애 판단 → 조치 제안 → 감사 기록` 중 한 흐름 |
| 김희준 | 실시간 시장 데이터·차트, 모의 주문, 기업 재무 분석과 역할별 AI 분석을 묶은 투자 분석 플랫폼 | 특정 시점의 시장·재무 자료를 모아 지표를 계산하고 기업 분석 결과를 만드는 흐름 | `종목 요청 → 자료 조회 → 지표 계산 → 기업 분석 결과 저장·조회` |
| 홍윤기 | 자연어로 AI 업무 흐름을 만들고 조직 권한에 맞는 자료만 RAG로 검색하며 비용·실행·감사 기록을 관리한 플랫폼 | 사용자 권한이 RAG와 MCP 실행, 감사 기록까지 이어지는 흐름 | `권한 확인 → RAG/MCP 실행 → 감사 기록` |

프로젝트별 정리 방법은 같습니다.

1. 사용자가 기능을 실행해서 결과를 받기까지의 과정을 그림으로 그립니다.
2. 해당 과정에 참여하는 API, 코드, DB 테이블과 외부 서비스를 연결합니다.
3. 정상 상황과 권한 실패, 중복 요청, DB 오류 상황을 테스트로 남깁니다.
4. 팀원이 설명하지 못하는 코드는 입력·출력·상태 변경부터 다시 확인합니다.
5. 새 프로젝트에 가져갈 개념, 더 공부할 부분, 버릴 구현을 구분합니다.

분담은 각자 자기 기술만 공부하겠다는 뜻이 아닙니다. 먼저 공부할 사람을
정해 학습 속도를 높이고, 만든 예제를 나머지 세 명이 실행하고 수정하면서
공통 지식으로 만드는 방식입니다.

### 4. 두 달 동안 진행할 신규 프로젝트

> **계획 작성 시점의 안내**
>
> 아래 주제와 기능, 기술 구성, 일정은 신청서를 작성하는 현재 시점의 예시와
> 가정입니다. 첫 달의 코드 분석, Java 실험, 공동 설계와 사용자 인터뷰 결과에
> 따라 실제 개발 내용은 달라질 수 있습니다. 중요하지 않거나 두 달 안에
> 완성하기 어려운 기능은 줄이거나 제외하고, 더 분명한 사용자 문제가
> 확인되면 프로젝트 주제 자체도 변경할 수 있습니다.

#### 4.1 만들고 싶은 것

프로젝트 제목은 **AI 개발 작업의 의사결정·코드·검증 기록 도구**로
정했습니다.

AI를 사용하면 코드를 빠르게 만들 수 있지만, 시간이 지나면 어떤 문제를
풀려고 했는지, 왜 그 방식을 선택했는지, 어느 코드와 커밋이 관련되어
있는지 찾기 어렵습니다. 프롬프트는 채팅에 남고, 설계 이유는 회의에 남고,
테스트 결과는 다른 곳에 있어 서로 연결되지 않는 경우가 많습니다.

이 도구는 개발 작업 하나를 기준으로 문제와 완료 조건, 중요한 프롬프트,
검토한 대안, 최종 결정, 변경한 파일과 커밋, 테스트 결과를 한곳에
연결합니다. 이후 다른 팀원이 `왜 이렇게 만들었는가`를 검색하고, 직접
코드를 확인했다는 기록을 남길 수 있게 합니다.

범용 메모 앱이나 새로운 코드 편집기를 만들려는 것은 아닙니다. 개발
과정에서 나온 문서·프롬프트·코드를 Git 작업과 연결해 다시 찾을 수 있게
만드는 데 집중합니다.

#### 4.2 사용 흐름

1. 개발자가 저장소에서 기록 도구를 시작합니다.
2. 작업 번호를 입력하고 해결할 문제와 완료 조건을 작성합니다.
3. 구현하면서 사용한 중요한 프롬프트와 검토한 대안을 기록합니다.
4. 변경 파일, 커밋과 실행한 테스트 결과를 연결합니다.
5. 작성자가 아닌 팀원이 코드를 실행하고 설명을 들은 뒤 검토 상태를
   남깁니다.
6. PR에서 기록과 검토가 빠지지 않았는지 확인합니다.
7. 나중에 질문이나 키워드로 과거 결정과 관련 코드를 찾습니다.
8. 필요하면 클라우드에 동기화해 여러 기기에서 보거나 문서 주소로
   공유합니다.

#### 4.3 반드시 만들 기능

| 기능 | 구현 방법 | 완료 기준 |
|---|---|---|
| 저장소 시작 | Java CLI가 기록 폴더와 설정 파일을 만듭니다. | 새 저장소에서 1분 안에 첫 기록 작성 |
| 작업 기록 | Markdown에 문제·완료 조건·프롬프트·대안·결정을 저장합니다. | Git diff로 변경 내용을 확인하고 수정 가능 |
| 코드 연결 | 파일 경로, 커밋과 테스트 명령·결과를 기록에 연결합니다. | 잘못된 파일·커밋 참조를 발견해 알려 줌 |
| 사람 검토 | 작성자와 검토자를 구분하고 실행·설명·수정 여부를 기록합니다. | 작성자가 자기 작업을 혼자 승인할 수 없음 |
| 검색 | 키워드, 태그, 저장소, 커밋과 상태로 찾습니다. | 미리 만든 질문에서 기대한 기록을 찾음 |
| 로컬 조회 화면 | Spring Boot가 저장소의 기록을 읽어 브라우저에 보여 줍니다. | 작업과 결정, 연결된 코드를 한 화면에서 확인 |
| 클라우드 동기화 | 로그인한 사용자의 로컬 변경을 서버와 주고받습니다. | 같은 요청이 반복돼도 중복되지 않고 충돌 시 덮어쓰지 않음 |
| 문서 호스팅 | 공개 또는 비공개 주소로 기록을 조회합니다. | 권한 없는 사용자를 차단하고 공개 범위를 변경 가능 |
| 내보내기·복구 | 저장소 원본과 서버 백업을 내보내고 다시 가져옵니다. | 빈 환경에서 복구 시험 통과 |

핵심 기능이 안정된 뒤에만 다음 기능 중 우선순위가 높은 것을 추가합니다.

- 근거 기록을 함께 보여 주는 RAG 검색
- 기록 목록·조회·검색을 제공하는 읽기 전용 MCP 서버
- GitHub PR에서 기록과 검토 상태를 확인하는 기능
- 팀별 세부 권한과 감사 기록 조회

이번 기간에는 범용 메모 편집기, 실시간 공동 편집, 프롬프트를 대신 실행하는
AI 에이전트, 자체 LLM 학습과 마이크로서비스 분리를 하지 않습니다.

#### 4.4 기본 구조

| 영역 | 선택 | 이유 |
|---|---|---|
| 언어와 서버 | Java, Spring Boot | 이번 과정에서 가장 깊게 익힐 기술이며 트랜잭션·보안·테스트를 함께 연습할 수 있음 |
| 코드 구조 | 모듈러 모놀리스 | 한 번에 배포하면서도 모듈 경계를 코드와 테스트로 확인할 수 있음 |
| CLI | Picocli | 별도 앱을 열지 않고 Git 작업 중 바로 기록하기 위함 |
| 원본 파일 | 저장소 안의 Markdown·JSON | 서비스가 없어져도 사람이 읽을 수 있고 Git 이력이 남음 |
| 로컬 검색 | 첫 달에 SQLite FTS와 Java 검색 도구를 비교한 뒤 하나를 선택 | 두 가지를 동시에 유지하지 않기 위함 |
| 서버 DB | PostgreSQL, JPA | 계정·공간·버전·권한·감사 기록 관리 |
| 화면 | React 기반의 최소 조회 화면 | 편집기 개발에 시간을 쓰지 않고 기존 프론트 경험 활용 |
| 권한 | Spring Security | 비공개 공간과 자료별 접근 제어 |
| 테스트 | JUnit, Testcontainers, ArchUnit, Playwright | 단위 기능, 실제 DB, 모듈 경계와 사용자 흐름을 나누어 확인 |
| 배포 | Docker Compose와 CI | 누구나 같은 환경에서 실행하고 배포할 수 있게 함 |

처음에는 하나의 서버와 하나의 DB 트랜잭션으로 처리합니다. Outbox와 재시도로
충분한 동안에는 SAGA를 억지로 넣지 않습니다. SAGA의 두 방식과 보상
트랜잭션은 모두 공부하되, 실제로 여러 외부 시스템의 상태를 함께 바꾸고
부분 실패를 되돌려야 할 때만 결정 문서를 작성한 뒤 사용합니다.

### 7. AI 사용 원칙

이전 프로젝트에서 가장 크게 반성한 부분이므로 네 명 모두 같은 규칙을
지킵니다.

1. AI를 사용하기 전에 사람이 문제와 완료 조건, 처음 생각한 해결 방법을
   먼저 적습니다.
2. 한 번에 큰 기능 전체를 요청하지 않고 검토할 수 있는 작은 변경으로
   나눕니다.
3. 중요한 프롬프트와 결과, 받아들인 이유와 버린 이유를 작업 기록에
   남깁니다.
4. 작성자는 코드의 입력·출력·DB 변경과 실패 흐름을 설명해야 합니다.
5. 작성자가 아닌 사람이 직접 실행하고 작은 부분을 수정한 뒤 병합합니다.
6. API, DB 구조, 권한과 외부 시스템 동작이 바뀌면 결정 문서를 남깁니다.

기능 완료 기준은 `동작하는 코드 + 자동 테스트 + 선택 이유 + 다른 팀원의
설명·수정 + 실패·복구 방법`입니다.

### 8. 시장성과 판매 가능성

[2025 Stack Overflow 개발자 설문](https://survey.stackoverflow.co/2025/ai)에서는
응답자의 84%가 AI 도구를 사용하고 있거나 사용할 계획이라고 답했습니다.
반면 AI 결과를 신뢰한다는 응답은 33%였고, 신뢰하지 않는다는 응답은 46%였습니다.
66%는 거의 맞지만 완전히 맞지 않는 답을, 45%는 AI가 만든 코드를 고치는 데
시간이 더 드는 문제를 경험했습니다. 저희가 겪은 문제가 다른 개발자에게도
반복되고 있다는 근거는 있습니다.

다만 시장에 빈자리가 그대로 있는 것은 아닙니다.
[GitHub Copilot Spaces](https://docs.github.com/en/copilot/concepts/context/spaces)는
저장소·코드·PR·이슈·메모를 AI가 참고할 자료로 묶고,
[Pieces](https://docs.pieces.app/)는 로컬에서 개발 활동을 기억하고 검색합니다.
따라서 단순한 개발자 메모장이나 프롬프트 보관함으로는 사용자를 모으기
어렵습니다.

저희가 확인하려는 차이는 `AI가 참고할 자료를 많이 모으는 것`이 아니라
`한 코드 변경의 문제·결정·테스트와 사람의 검토를 연결하는 것`입니다.
이 차이가 실제로 필요한지는 아직 증명되지 않았습니다. 그래서 시장성이
있다고 단정하지 않고 다음 순서로 확인합니다.

1. 첫 주 인터뷰 10명 중 6명 이상이 최근 비슷한 문제를 겪었는지 확인합니다.
2. 팀이 모든 AI 활용 PR에 4주간 직접 사용합니다.
3. 외부 개발자 5명이 설치하고, 그중 2명 이상이 다음 주에도 다시 쓰는지
   확인합니다.
4. 소규모 개발팀 한 곳이 유료 시험 사용을 하거나 세 곳이 비용을 낼 의향을
   문서로 남기는지 확인합니다.

로컬 CLI와 직접 설치할 수 있는 서버는 Apache-2.0으로 공개하는 방향을
우선 검토합니다. 유료 기능은 관리형 클라우드 동기화, 비공개 호스팅, 백업,
팀 권한과 감사 기록입니다. AI 기능 자체보다 설치·운영·권한·복구를 직접
관리하지 않아도 되는 편의에 비용을 받을 수 있는지 확인하겠습니다.

현재 판단은 **조건부로 진행할 만하다**입니다. 취업과 학습 관점에서는
Java·DB·보안·검색·클라우드 운영을 하나의 실제 문제로 보여 줄 수 있어
가치가 있습니다. 오픈소스로 외부 사용자를 얻을 가능성도 있습니다. 다만
두 달 안에 판매까지 성공한다고 약속할 수는 없으며, 반복 사용과 지불 의향이
확인되지 않으면 판매 기능을 더 만들지 않겠습니다.

개인 결과물은 문서 앞부분에 각자 다르게 적었습니다. 담당자는 해당 결과물을

인정합니다.

첫 달에는 기존 프로젝트를 기능 목록이 아니라 문제, 판단, 실패와 검증

이력서 문장과 면접 사례로 매주 갱신합니다. 마지막에는 프로젝트를 3분과
10분으로 설명하는 발표를 준비하고, 아키텍처·트랜잭션·권한·AI 사용과
사용자 검증에 관한 질문에 네 명 모두 답할 수 있도록 연습합니다.
