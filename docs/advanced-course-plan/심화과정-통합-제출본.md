# 크래프톤 심화과정 프로젝트 계획서

**교육생: 최우녕**

## 개인 목표

Opsia에서 경험한 운영·관측·복구 역량을 Java/Spring 기반의 아키텍처 설계와 코드 이해 역량으로 전환합니다. 기능을 많이 만드는 것보다 팀 전체가 구조와 실패 경로를 설명할 수 있는 시스템을 완성하고, 이를 Java 백엔드·플랫폼 직무 포트폴리오로 연결합니다.

## 기존 경험과 개선 방향

기존 프로젝트에서 Kubernetes evidence, RCA, GitOps, outbox, retry와 관측 기능을 구현했습니다. 그러나 구현 범위가 넓어지면서 모든 팀원이 전체 구조를 코드 수준에서 공유하지 못한 한계가 있었습니다. 이번에는 AI가 만든 결과를 받아들이는 역할이 아니라, 아키텍처 결정과 코드의 동작을 직접 검증하는 개발자가 되는 것을 개인 목표로 둡니다.

## 개인 중점

- 모듈 경계, transaction, outbox와 관측 가능성
- architecture fitness test와 운영·복원 검증
- 주간 아키텍처 설명 세션과 코드 교차 리뷰 진행

## 공통 학습 및 프로젝트 계획

이하의 학습 내용, 일정과 성공 기준은 네 명 모두 동일합니다. 담당 영역은
나누되 학습 범위와 코드 이해 책임은 나누지 않습니다.

### 1. 정글 수료 직후의 공통 목표와 회고

네 명 모두 정글에서 자료구조·알고리즘, C·컴퓨터 구조, PintOS 운영체제,
웹·DBMS, LLM·RAG·MCP와 AI 팀 프로젝트를 이수했습니다. 심화과정은 이를
다시 배우는 과정이 아니라 **CS 원리와 AI 활용 경험을 Java/Spring의
설계·운영 역량으로 전환하는 과정**입니다.

- 정글에서 익힌 메모리·thread·동시성·network·DB 원리를 JVM과 Spring의
  실제 동작에 연결합니다.
- 네 명 모두 요구사항, module 경계, 데이터 흐름과 실패·복구 경로를 코드
  수준에서 설명하고 비담당 코드를 수정합니다.
- AI는 탐색·초안·반복 작업을 돕는 도구로만 사용하고 설계 판단과 코드
  소유권은 사람이 갖습니다.
- 시연용 포트폴리오가 아니라 팀이 매일 사용하고 외부 개발자의 반복
  사용을 검증한 오픈소스 제품을 만들고 cloud 판매·취업까지 연결합니다.

이전 프로젝트는 기능 구현에는 성공했지만 전체 아키텍처와 코드를 모든
팀원이 이해하지 못했습니다. AI에게 설계와 구현을 과도하게 맡기면서 결정
근거가 사라지고 담당자가 아닌 코드를 분석·수정하기 어려워졌습니다. 이번
과정에서는 기능 수보다 **팀 전체의 이해와 변경 가능성**을 우선합니다.

### 2. 프로젝트 후보안

- 후보명: **DevArchive**(가칭, 검증 후 변경 가능)
- 정의: AI 개발 과정의 문제, prompt, 설계 결정, ADR, code·commit 참조와
  검증 결과를 Git repository에 연결해 보존·검색·공유하는 오픈소스 도구
- 사용자: AI coding tool을 쓰는 개인 개발자와 2~10명 개발팀
- 핵심 문제: AI가 빠르게 코드를 만들수록 설계 의도와 사람의 이해가
  사라져 코드를 설명·검토·수정하기 어려워지는 문제

사용자는 repository에서 문제와 완료 조건을 기록하고, 중요한 prompt·대안·
결정·파일·commit·테스트를 하나의 작업 기록으로 연결합니다. reviewer가
사람의 이해와 검증 결과를 승인하며, 이후 `왜 이렇게 구현했는가`를 근거와
함께 검색합니다.

범용 노트 앱·새 IDE·AI agent 자체는 만들지 않습니다. 현재의 넓은
`editor+sync+hosting+RAG+MCP` 기획은 3개월에 성공시키기 어렵고 대체재도
많습니다. `Git workflow 안에서 decision-to-code trace와 사람의 이해를
검증한다`는 한 문제로 축소했을 때만 진행합니다.

### 3. 네 명이 동일하게 학습할 내용

| 학습 영역 | 공통 학습·적용 내용 |
|---|---|
| CS→JVM 전환 | PintOS의 thread·memory 경험을 JVM memory model·GC·thread pool·profiling과 연결 |
| 아키텍처 | 품질 속성, coupling·cohesion, C4·ADR, dependency rule과 package-by-feature |
| Spring·DBMS | MVC request 흐름, transaction·isolation, JPA locking, index와 query plan |
| 일관성·분산 | idempotency, outbox, retry·DLQ, SAGA·보상 transaction과 failure model |
| AI 시스템 | 기존 RAG·MCP 경험을 evaluation·citation·권한·승인·audit로 심화 |
| 검증·운영 | characterization·통합·E2E·ArchUnit test, metric·trace와 backup·restore |
| 제품·오픈소스 | 문제 인터뷰, activation·retention, license, contribution과 release |

- **《소프트웨어 아키텍처 101》**으로 정글에서 구현하며 경험한 성능·
  안정성·변경 용이성의 trade-off를 공통 언어와 C4·ADR로 정리합니다.
- **《클린 아키텍처》**의 dependency rule을 실제 package와 use case에
  적용하되, 이유 없이 계층과 interface를 늘리지 않습니다.
- **SAGA**는 전원이 choreography·orchestration과 보상 transaction을
  학습하지만 초기 modular monolith에는 사용하지 않습니다. 독립 서비스와
  외부 부수효과가 실제로 생길 때 ADR 작성 후 도입합니다.

매주 독서 내용 하나를 PintOS·웹·AI 프로젝트 경험과 연결해 작은 Java
실험으로 검증하고 15분 teach-back을 수행합니다. 비담당자가 설명하지
못하면 학습 완료가 아닙니다.

### 5. 초기 아키텍처와 MVP

- Spring Boot **modular monolith**로 시작하고 workspace, record, search,
  identity, publish 모듈을 분리합니다.
- 원본은 repository의 Markdown·JSON, SQLite는 로컬 검색 index로
  사용합니다.
- Java·Picocli CLI로 `capture·link·search·verify`를 먼저 제공합니다.
- 로컬 사용이 검증된 뒤 Spring Boot·PostgreSQL cloud adapter로 sync,
  private workspace와 문서 hosting을 제공합니다.
- MCP는 읽기·검색부터 만들고, 쓰기는 preview·승인·audit 없이는
  실행하지 않습니다.
- 한 DB transaction과 outbox로 먼저 해결하며 필요하기 전에는
  microservice와 SAGA를 구현하지 않습니다.

### 8. 성공 및 변경 기준

학습·코드 기준:

- 네 명 모두 임의의 기능에서 HTTP 요청·thread·transaction·DB·AI 외부
  I/O·실패 복구까지 설명합니다.
- 비담당 모듈에서 각자 최소 한 번 수정 PR을 완료합니다.

사용·판매 기준:

- 외부 개발자 또는 팀 3곳이 4주 동안 매주 사용합니다.
- 최소 1곳의 유료 design partner 또는 3곳의 서면 pilot·지불 의향을
  판매 검증 목표로 둡니다.
- star와 다운로드 수는 참고 지표이며 반복 사용을 대신하지 않습니다.

변경 기준:

- 8월 24일까지 인터뷰 10명 중 6명에게 문제가 반복되지 않으면 주제를
  변경합니다.
- 10월 15일까지 팀 내부 사용이 유지되지 않으면 cloud·RAG·MCP를 중단하고
  local core부터 수정합니다.
- 제품이 Git·PR 흐름보다 번거로우면 별도 앱을 늘리지 않고 CLI·GitHub
  integration을 단순화합니다.
- 주제가 바뀌어도 Java 포팅, 공통 아키텍처 학습, AI 사용 원칙과
  오픈소스 공개 목표는 유지합니다.

### 9. 오픈소스·판매·취업 연결

local core와 self-host server는 공개 license로 제공하고, 관리형 sync,
private hosting, backup, 팀 권한과 audit를 판매 가설로 검증합니다.
결제부터 만들지 않고 반복 사용과 지불 의향을 먼저 확인합니다.

포트폴리오에는 정글의 OS·웹·AI 학습이 Java 제품 설계로 이어진 과정,
사용자 문제, 범위를 버린 판단, modular monolith와 SAGA 적용 여부의
trade-off, AI 코드 통제 방식, 사용·복원 지표와 외부 pilot 결과를 제시합니다.

### 5. 초기 아키텍처와 MVP

  identity, publish 모듈을 분리합니다.

  사용합니다.
- Java·Picocli CLI로 `capture·link·search·verify`를 먼저 제공합니다.
- 로컬 사용이 검증된 뒤 Spring Boot·PostgreSQL cloud adapter로 sync,
  private workspace와 문서 hosting을 제공합니다.
- MCP는 읽기·검색부터 만들고, 쓰기는 preview·승인·audit 없이는
  실행하지 않습니다.
- 한 DB transaction과 outbox로 먼저 해결하며 필요하기 전에는
  microservice와 SAGA를 구현하지 않습니다.

# 크래프톤 심화과정 프로젝트 계획서

**교육생: 홍윤기**

## 개인 목표

Nodease에서 경험한 RBAC, workflow, RAG와 audit을 Java/Spring Security 기반 설계로 전환합니다. 권한·동기화·감사 코드를 다른 팀원도 이해할 수 있게 만들고, Java 보안 백엔드·AI workflow 플랫폼 직무에 연결합니다.

## 기존 경험과 개선 방향

Nodease에서 조직·팀 권한, LLM credential, RAG와 migration을 폭넓게 구현했습니다. 이번에는 특정 담당자만 아는 보안 모듈을 만들지 않고, 불변조건과 실패 시나리오를 테스트와 문서로 공유합니다. AI가 생성한 보안 코드는 그대로 병합하지 않고 위협 모델과 코드 walkthrough를 통과시킵니다.

## 개인 중점

- Spring Security, resource permission과 감사 이력
- 동기화 idempotency, 충돌과 복원 시나리오
- threat model과 권한 우회 교차 테스트

## 공통 학습 및 프로젝트 계획

이하의 학습 내용, 일정과 성공 기준은 네 명 모두 동일합니다. 담당 영역은
나누되 학습 범위와 코드 이해 책임은 나누지 않습니다.

### 1. 정글 수료 직후의 공통 목표와 회고

네 명 모두 정글에서 자료구조·알고리즘, C·컴퓨터 구조, PintOS 운영체제,
웹·DBMS, LLM·RAG·MCP와 AI 팀 프로젝트를 이수했습니다. 심화과정은 이를
다시 배우는 과정이 아니라 **CS 원리와 AI 활용 경험을 Java/Spring의
설계·운영 역량으로 전환하는 과정**입니다.

- 정글에서 익힌 메모리·thread·동시성·network·DB 원리를 JVM과 Spring의
  실제 동작에 연결합니다.
- 네 명 모두 요구사항, module 경계, 데이터 흐름과 실패·복구 경로를 코드
  수준에서 설명하고 비담당 코드를 수정합니다.
- AI는 탐색·초안·반복 작업을 돕는 도구로만 사용하고 설계 판단과 코드
  소유권은 사람이 갖습니다.
- 시연용 포트폴리오가 아니라 팀이 매일 사용하고 외부 개발자의 반복
  사용을 검증한 오픈소스 제품을 만들고 cloud 판매·취업까지 연결합니다.

이전 프로젝트는 기능 구현에는 성공했지만 전체 아키텍처와 코드를 모든
팀원이 이해하지 못했습니다. AI에게 설계와 구현을 과도하게 맡기면서 결정
근거가 사라지고 담당자가 아닌 코드를 분석·수정하기 어려워졌습니다. 이번
과정에서는 기능 수보다 **팀 전체의 이해와 변경 가능성**을 우선합니다.

### 2. 프로젝트 후보안

- 후보명: **DevArchive**(가칭, 검증 후 변경 가능)
- 정의: AI 개발 과정의 문제, prompt, 설계 결정, ADR, code·commit 참조와
  검증 결과를 Git repository에 연결해 보존·검색·공유하는 오픈소스 도구
- 사용자: AI coding tool을 쓰는 개인 개발자와 2~10명 개발팀
- 핵심 문제: AI가 빠르게 코드를 만들수록 설계 의도와 사람의 이해가
  사라져 코드를 설명·검토·수정하기 어려워지는 문제

사용자는 repository에서 문제와 완료 조건을 기록하고, 중요한 prompt·대안·
결정·파일·commit·테스트를 하나의 작업 기록으로 연결합니다. reviewer가
사람의 이해와 검증 결과를 승인하며, 이후 `왜 이렇게 구현했는가`를 근거와
함께 검색합니다.

범용 노트 앱·새 IDE·AI agent 자체는 만들지 않습니다. 현재의 넓은
`editor+sync+hosting+RAG+MCP` 기획은 3개월에 성공시키기 어렵고 대체재도
많습니다. `Git workflow 안에서 decision-to-code trace와 사람의 이해를
검증한다`는 한 문제로 축소했을 때만 진행합니다.

### 8. 성공 및 변경 기준

학습·코드 기준:

- 네 명 모두 임의의 기능에서 HTTP 요청·thread·transaction·DB·AI 외부
  I/O·실패 복구까지 설명합니다.
- 비담당 모듈에서 각자 최소 한 번 수정 PR을 완료합니다.
- AI가 생성했지만 아무도 설명하지 못하는 production code가 없습니다.

사용·판매 기준:

- 팀원이 4주 이상 사용하며 1인당 기록 30개와 재사용 20회를 남깁니다.
- 외부 개발자 10명이 onboarding을 시도하고 5명이 첫 기록을 만듭니다.
- 외부 개발자 또는 팀 3곳이 4주 동안 매주 사용합니다.
- 최소 1곳의 유료 design partner 또는 3곳의 서면 pilot·지불 의향을
  판매 검증 목표로 둡니다.
- star와 다운로드 수는 참고 지표이며 반복 사용을 대신하지 않습니다.

변경 기준:

- 8월 24일까지 인터뷰 10명 중 6명에게 문제가 반복되지 않으면 주제를
  변경합니다.
- 10월 15일까지 팀 내부 사용이 유지되지 않으면 cloud·RAG·MCP를 중단하고
  local core부터 수정합니다.
- 제품이 Git·PR 흐름보다 번거로우면 별도 앱을 늘리지 않고 CLI·GitHub

### 9. 오픈소스·판매·취업 연결

local core와 self-host server는 공개 license로 제공하고, 관리형 sync,
