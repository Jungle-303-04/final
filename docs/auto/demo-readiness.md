## 게임 부하 실측

CPU request 100m, HPA 최소 2·최대 10 조건에서 측정했다. CPU 제한 500m에서는 50봇에서
소유 파드 readiness가 실패했으므로 2코어로 올렸고, 발표 부하는 검증된 20~50봇만 사용한다.

| 봇 | HPA CPU | 파드 수 | 전체 CPU | 최대 파드 CPU | 결과 |
|---:|---:|---:|---:|---:|---|
| 5 | 60% | 2 | 119m | 100m | 통과 |
| 10 | 68% | 2 | 168m | 150m | 통과 |
| 20 | 105% | 3 | 240m | 207m | 통과, 자동 증설 |
| 50 | 79% | 4 | 603m | 443m | 통과, 방 조회 HTTP 200 |
| 100 | 121% | 9 | 1056m | 780m | 실패, 30초 안에 방 조회 404 |

실측에 따라 HPA CPU 목표는 70%에서 50%로 확정했다. 100봇은 CPU 제한을 500m, 1코어,
2코어로 바꿔 세 번 확인했지만 같은 실패가 반복됐다. 단일 방 이벤트 루프 한계로 판정하고
발표 대본에서 제외한다.

## 화면·배포 판정

- Pending 파드 0개. PriorityClass 적용, ResourceQuota·LimitRange 없음, 새 파드 즉시 Scheduled.
- PDB `minAvailable: 1` 적용. 롤링 업데이트 중 방 조회 11/11회 성공.
- Opsia 리소스 표에서 게임 파드 CPU·메모리 실측값을 확인했다. 다만 서버 배치 카드의 일부
  게임 파드는 `사용률 —`여서 채움색 판정은 부분 실패다.
- Applications 화면은 게임의 표준 app 라벨이 존재하지만 현재 필터에서 0개로 표시된다.
  발표에서 Applications 동선은 제외한다.
- 방 생성, `/watch/:roomCode`, `/play/:roomCode`는 모두 성공했고 공개 `/admin`은 404를 유지한다.

## 데모 후 구조 작업

현재 한 방은 lease 소유 프로세스가 권위를 가진다. 여러 게임 서버가 한 방의 계산을 함께
처리하지 않으므로 발표에서는 자동 용량 확보만 설명한다. 공유 상태와 pub/sub 기반 구조 변경은
데모 후 별도 작업으로 진행한다.
